# Deployment contract and operator preflight

All three profiles run identical backend/frontend/worker code and migration head. These Compose files are complete service definitions, not proof of production readiness. Real TLS, private networking, credentials and provider acceptance must be supplied before use. No deployment is performed by CI; CI parses configuration, builds/scans images and runs disposable engine tests.

## Placement

AIO `deploy/aio/compose.yml`: one host, single SeaweedFS master/volume, independent external backup. No HA claim. Only the app/office gateway publishes user-facing 80/443. S3 is an unpublished internal TLS gateway. SCIM 9443 and Office backchannel 8444 bind only the private address.

PROD-COMPACT: `app.compose.yml` on app+office; `data.compose.yml` on PostgreSQL/OpenSearch/master03; `storage01.compose.yml` on master01/volume01/filer/S3; `storage02.compose.yml` on master02/volume02. PROD-DISTRIBUTED adds a separate `office.compose.yml`; app omits the local editor. Masters use quorum peers and replication **001** across the two physical volume servers. Filer metadata is persisted independently. These are per-host Compose projects: a local Docker bridge does not span machines.

## Required host controls

Provision an authenticated WireGuard/private VLAN transport and a host firewall before starting production profiles. Use fixed private addresses/DNS and certificates with correct SANs for every advertised host/container alias. Cross-host private bindings are **not** a substitute for source allowlists: Docker published ports can bypass a simple UFW rule; enforce DOCKER-USER/nftables and upstream network ACLs. Permit only the explicit trusted application/storage peers. User networks may reach only app/Office HTTPS. Do not bind private ports to 0.0.0.0 or a user-facing address.

Private service ports: PostgreSQL 5432 (app/backup only), OpenSearch 9200 (indexer/backend/bootstrap only), masters 9333/19333 (storage peers), volumes 8080/18080 (master/filer peers), filer 8888/18888 (S3/storage peers), S3 8333 (backend/workers/backup only), SCIM 9443 (Authentik only, mTLS plus static capability), Office backchannel 8444 (Office only, TLS/source allowlist plus signed per-session tokens). Redis, Tika and ClamAV publish no host ports and occupy separate internal cache/parser/AV networks. Tika and ONLYOFFICE have no egress network. On AIO/COMPACT, the editor calls the private TLS backchannel through its app-network DNS alias; use OFFICE_CIDR=172.29.0.20/32 and local http://onlyoffice for backend cache retrieval. On DISTRIBUTED, an unpublished TLS office-relay accepts only editor internal routes and proxies to the fixed APP_PRIVATE_ADDRESS:8444 with verified backend TLS; the app host allows only the Office host private address. The relay does not accept arbitrary destinations or public/user API paths. Backend access is exclusively through gateways; forwarded client IP is trusted only from fixed app gateway 172.29.0.2 and SCIM gateway 172.29.0.4. Confirm no existing network conflicts with 172.29.0.0/24. Office backchannel does not receive privileged proxy trust.

Bind the production file selected for the actual host, with a host-specific `.env` copied from `.env.example`. `PUBLIC_IP`, `PRIVATE_IP`, master peers, DNS and CIDRs are topology, not credentials. Configure split-horizon DNS: AIO S3/search aliases point at internal service networks; production service names point at the private host addresses. All gateway templates reject SCIM/editor internal routes on the public app edge. No permanent S3 URL or credential is provided to the browser.

## Files and identities

Use encrypted host disks and an independent encrypted WAL mount. Pre-provision mounts; a nonexistent bind directory is not acceptable for keys/configuration. Keep real `.env`, private directories and certificates outside Git and Docker build contexts.

- `SETTINGS_DIR`: directory owned UID/GID **10001**, mode **0700**; scalar files mode **0400/0600**, one file per Settings field. Required secret fields: `database_url`, `csrf_secret`, `oidc_client_secret`, `s3_access_key`, `s3_secret_key`, `office_browser_secret`, `office_outbox_secret`, `opensearch_password`, `scim_token`. Optional mail/Telegram credentials are likewise files. No symlinks, hardlinks, unknown names or world/group permissions. Example DB URL structure is `postgresql+asyncpg://USER:PASSWORD@PRIVATE_DB/DB?ssl=verify-full`; use actual vault values, never development defaults.
- `AUDIT_DIR`: UID/GID 10001, mode 0750; application JSONL file 0640. Install the host Wazuh Agent using `deploy/wazuh/agent.conf`; forward to the independent authenticated Wazuh manager. Host agent access is an infrastructure privilege, not a user API. Preserve append-only/off-host audit policy and disk-full alerts.
- `TRUST_DIR`: public CA material only, including `ca.crt` and `ca-bundle.crt` (public roots plus internal trust chain). No private keys. Readable by UID 10001, Office and backend; only operators may write it. OIDC/Office clients explicitly load this CA rather than allowing environment proxy redirects. S3 and PostgreSQL verify private TLS certificates.
- `TLS_DIR`: gateway certificate with all relevant hostnames, `server.key` accessible only to gateway UID **101**, and `provisioning-ca.crt` for allowed Authentik clients. Private key 0400. Restrict the directory to the service identity; backend receives the separate public trust directory.
- `DB_TLS_DIR`: certificate/key readable by the image's postgres UID (Alpine **70**), key 0600; CA public. `DATABASE_PASSWORD_FILE` is a restricted vault file for PostgreSQL initialization. Use least-privileged application and dedicated backup/replication roles after schema bootstrap; the image bootstrap superuser is not an application role and must not be used for daily API access.
- `SEARCH_TLS_DIR` / `SEARCH_SECURITY_DIR`: readable by UID **1000**, no demo certificates/accounts. Copy `opensearch.example.yml` into the private configuration and provision security index/users with the dedicated admin certificate through official `securityadmin.sh`. Application indexer credentials must have only required `nambadrive-documents-v1` index rights, never cluster administration. Keep the security plugin enabled. Index authorization still comes from backend checks.
- `WEED_TLS_DIR`: distinct server/client identity certificates, keys readable by UID **10001**, private mode 0400. Copy `seaweed/security.example.toml` privately and review exact allowed common names, CA and SANs; fields match SeaweedFS **4.48** scaffold (`allowed_commonNames`). HTTPS and gRPC use authenticated TLS; no insecure verification fallback. S3 configuration must contain explicit private credentials/actions (no anonymous identity), separate DATA/quarantine buckets, backend rights and separate backup credentials. Disable unused IAM/catalog endpoints. Master/volume/filer UIs are private; no directory metadata exposure.
- `OFFICE_CONFIG_FILE`: private 0600 JSON from `deploy/aio/onlyoffice/local.example.json`. Browser/inbox key must match the backend browser key; outbox must be **different** and match backend outbox. Generate at least 32 random bytes encoded as hex/base64url. All three token checks must be true. The derived image patches exactly one vendor outbox assignment, refuses an unexpected startup/logging layout and keeps JWT enabled. Its private wrapper loads keys without printing them; default vendor request logs are disabled because signed capabilities can appear in URLs. Application audit and health provide controlled evidence. Root/writable filesystem exceptions are limited to required vendor startup services; all capabilities are dropped except explicitly listed startup capabilities. Community is the approved DEV/MVP edition; production editor capacity/licensing needs separate acceptance.

Never put secrets on command argv or print `docker compose config` with actual credential environment values. Files are mounted read-only. PostgreSQL WAL is written only to its dedicated independent encrypted mount owned by postgres, 0700; the same mount is included in daily backup. Monitor archive failure/lag and disk capacity; no automatic WAL deletion.

## Bootstrap and checks

Before first startup, run `python scripts/deploy/check_profiles.py`, then `docker compose --env-file HOST.env -f HOST.compose.yml config --quiet`. On a fresh host, explicitly run the `bootstrap` profile's `volume-bootstrap` one-shot service for empty SeaweedFS/OpenSearch volumes. It refuses nonempty volumes rather than changing ownership of existing data. Start infrastructure, initialize private S3 buckets/OpenSearch identities, then run `backend alembic upgrade head` using the migration role and provide a separate least-privileged runtime role. Finally start backend/workers/frontend/gateways. This is an operator runbook; no script silently migrates or deploys production.

Verify actual readiness, every host firewall path, TLS hostname/chain, SCIM mTLS/source/token denial, S3 anonymous denial, editor signed callbacks and Wazuh receipt before user access. Run daily complete backups and quarterly isolated restore per `docs/phase20-backup-restore.md`. Test a storage node outage and master quorum on UAT before claiming production resilience. AIO has no such HA claim.

Images are content-pinned in `images.lock.json`; Python runtime dependencies are pinned in `backend/requirements.lock`, frontend uses `npm ci`. Refresh pins only with migration/regression/SCA/container gates. CI publishes container vulnerability reports, blocks every unresolved Critical and requires review of High findings; a High authorization bypass is never acceptable. No ignore list is supplied. Real multi-host runtime/TLS/Office/provider acceptance remains pending; parsed Compose and successful builds do not establish it.
